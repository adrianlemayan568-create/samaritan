# M2.4 — Structured propositions and deterministic reasoning

## Scope

M2.4 establishes the analytical contract layer between validated evidence and later probabilistic or decision-oriented reasoning. M7 adds persistent EvidenceSet selection records to SQLite and advances the database schema from version 1 to version 2 without rewriting existing source records. Proposition, hypothesis, finding, and evaluation records remain outside the current persistence scope.

## Proposition semantics and construction are separate

    EvidenceSet
        -> exact construction definition + exact semantics definition
        -> source resolution
        -> typed role binding
        -> field-level provenance
        -> semantic validation
        -> structured Proposition

A PropositionSemantics definition owns the meaning of a proposition type and version: declared roles, role kinds and types, temporal constraints, temporal scope, and typed parameters. A PropositionConstructionDefinition owns only the finite source bindings used to populate those semantic fields. Construction cannot add or reinterpret fields.

Registries reject duplicate identities. A constructor must request the exact construction ID/version and the exact proposition type/semantics version. There is no fallback to a newer or older semantics version. Semantics identifiers (proposition type, role names, entity/event types, and parameter names) must be Unicode NFC normalized and bounded to 128 characters. They permit Latin letters, ASCII digits, underscore, dot, and hyphen; other scripts and control/confusable characters are rejected to reduce visually ambiguous registry keys. Registry keys, fingerprints, and deterministic identities therefore use the same representation.

## Structured proposition identity

A Proposition contains:
- proposition type and exact semantics version;
- named entity and event role values;
- concrete UTC temporal scope and boundary inclusivity;
- field-level source event, observation, and relationship provenance;
- exact construction ID/version for audit.

The current proposition ID algorithm, uuid5-v2, is a deterministic UUID5 over semantic identity: proposition type/version, the canonical SHA-256 fingerprint of the exact semantics definition, role names and concrete role values, temporal scope, and parameters. The fingerprint excludes human-readable description text and uses canonical Unicode NFC and JSON serialization. The identity algorithm version is stored on each proposition. The legacy uuid5-v1 algorithm remains available for historical compatibility, but hypothesis evaluation rejects it; new construction always uses uuid5-v2. Construction history and generation history are deliberately excluded.

StructuredHypothesis owns a structured Proposition. HypothesisGeneration remains a separate record describing how a candidate was generated; it is not part of proposition identity.

## Initial supported construction

The first registered construction is account_authentication_sequence@1. The finite construction contract also supports registered top-level event-attribute parameters, integer temporal-difference parameters derived from event timestamps, and string parameters sourced from explicit directed relationship records. Relationship retrieval is performed through the repository; each such parameter retains the relationship and observation IDs in its field provenance.

It requires exactly one each of:
- authentication_failure, with participant role target;
- authentication_success, with participant role target;
- host_activity, with participant role subject.

Each participant must resolve to exactly one entity of type user_account, and all three mappings must resolve to the same entity ID. A missing or ambiguous event, missing or ambiguous participant, absent entity, wrong entity type, or inconsistent account identity fails construction.

The failure must strictly precede success, which must strictly precede host activity. Each consecutive interval is at most 300 seconds. The temporal scope runs from failure to host activity, inclusive at both boundaries.

Every proposition role has field-level provenance. The account field retains all three source event IDs and their observation IDs. Event roles retain their own event and observation references. Construction and provenance validation share a deterministic resolver. Event type narrows candidates, while registered participant-role bindings constrain them; candidates must also satisfy cross-role entity consistency. Exactly one complete valid assignment is required. Multiple valid assignments fail as ambiguous. Optional event roles are included when a globally consistent assignment can satisfy them and omitted only when no such assignment exists. Unrelated events and participant mismatches do not create false ambiguity.

This construction does not infer a common actor, host ownership, authorization, or malicious intent from shared account identity.

## Findings and evaluation

The new proposition_contracts.py and reasoning_contracts.py modules provide the structured M2.4 path. The earlier evaluation_contracts.py contracts remain intact for compatibility; in particular, CriterionEvaluationResult is not modified. The new path uses its own structured Proposition and StructuredHypothesis contracts.

The new reasoning_contracts.py model is stance-neutral:
- CriterionDefinition describes an independently testable condition, its typed JSON parameters, a unique reviewed independence assertion identifier, and whether its evidence is attacker-influenceable.
- CriterionOutcomeDefinition defines finite outcome codes scoped to a criterion type and vocabulary version.
- CriterionFinding records only a factual matched, not_matched, or insufficient result. An insufficient finding has no outcome code and must identify missing information.
- Findings can be reused. They do not contain proposition-specific stance.

A BearingDefinition maps one criterion outcome to judgments for the focal proposition and one alternative. Judgments are ordinal consistency categories: expected, compatible, unexpected, and incompatible. Each bearing records its rationale, basis, author, review state, and whether the criterion is required or contextual.

For completeness, a criterion is considered required if at least one of its registered bearings is marked required. A missing or insufficient finding for that criterion therefore makes the evaluation incomplete, even if other bearings for the same criterion are contextual. A criterion whose bearings are all contextual may be missing without automatically preventing a supported conclusion. Each criterion must declare a distinct independence_assertion_id. This identifier records a reviewed independence assertion in the rule definition; it does not create a dependency group. The current M2.4 contract does not model dependent criteria, and it does not infer independence or dependence from shared event references. When a complete finding exists, diagnosticity uses only the bearings matching that finding's actual outcome and the applicable alternatives.

The implicit residual alternative uses the reserved ID __residual__. Its alternative judgment is fixed to compatible; it is not an editable declared alternative. Its focal judgment must agree with the focal judgment assigned to the declared alternatives for the same criterion outcome. Evaluation rules bind to a proposition type and exact semantics version, not to a hypothesis-generation rule. Rule IDs and versions are preserved in an immutable registry keyed by (evaluation_rule_id, rule_version): one logical rule ID may have multiple immutable versions, but an exact ID/version cannot be overwritten. Materially changed logic receives a new versioned identity. Focal-judgment consistency is enforced across all bearing rows for the same criterion outcome, including the residual alternative.

Production synthesis requires approved evaluation rules and approved bearings. Experimental synthesis may use reviewed definitions. Before evaluation, every registered outcome for each criterion must have a bearing for every declared alternative and the residual; every built-in evaluator output must also exist in that finite outcome vocabulary. CriterionEvaluatorRegistry binds a criterion type and exact evaluator version to a finite built-in evaluator type and an exact typed parameter interface. CriterionEvaluationEngine dispatches only to the supported built-ins: event attribute equality/presence, entity-scoped event-type counts, participant-role/entity-role matching, and temporal-gap checks. Event-type counts require an entity role, count only selected events involving that entity within the proposition's temporal scope, and return insufficient when any proposition event role is absent from the selected EvidenceSet. Temporal ordering violations have a distinct outcome from positive gaps that exceed a configured limit. HypothesisEvaluationEngine verifies every focal and alternative proposition against the exact registered semantics definition, requires the evaluation EvidenceSet to match the focal proposition manifest, runs the registered criteria, synthesizes the findings, and returns an immutable HypothesisEvaluationRecord containing the EvidenceSet ID, exact evaluation_rule_id/version, findings, and synthesis. Finding, evaluation, and assessment IDs are deterministic; callers can inject a clock to make their timestamps reproducible. Registries are frozen when handed to construction, validation, or evaluation engines. No arbitrary callbacks, free-form expressions, or LLM-generated evaluator bindings are introduced.

## Diagnosticity synthesis

DiagnosticitySynthesizer uses explicit ordinal comparisons, not numerical scores or probabilities.

For each declared alternative, it aggregates findings into:
- favors_focal;
- favors_alternative;
- non_discriminating;
- conflicting.

A complete finding that makes the focal proposition incompatible can produce not_supported only when its criterion is not attacker-influenceable. Missing or insufficient required findings prevent a supported conclusion. Supported requires the focal proposition to be favored over every declared alternative; it does not mean the proposition is proven true.

The residual is always compatible and does not block a supported result. The confidence ceiling remains low unless at least one finding is more expected under the focal proposition than under the residual; such evidence may raise it only to moderate. High confidence is not representable in M2.4 and is reserved for a future calibrated milestone. `HypothesisEvaluationRecord.validate_against` requires the caller to supply the exact outcome registry and production/experimental mode used for evaluation; it re-runs deterministic synthesis from the record's findings and requires exact equality with the stored synthesis, including standings, finding references, reason codes, ceiling, outcome, and summary. Evaluation mode is validation context and is not currently stored on the record.

## Evidence-manifest boundary

A proposition preserves the exact ordered EvidenceSet references used at construction, including event-level and observation-level granularity. The manifest is deliberately excluded from deterministic semantic proposition identity, so the same semantic proposition may have different evidence manifests. As the construction commit point, PropositionConstructor persists the supplied EvidenceSet before constructing the proposition. The repository stores the EvidenceSet identity and creation time separately from ordered item rows; each item retains exactly one observation or event reference, and foreign keys anchor those references to existing source records. Identical persistence retries are idempotent, while reusing an EvidenceSet ID for different content is rejected. Empty EvidenceSets remain valid repository records, although a proposition manifest must be non-empty. Provenance validation retrieves the stored EvidenceSet by ID and requires exact equality of the ordered reference tuple before resolving the manifest. HypothesisEvaluationEngine independently checks that the supplied focal EvidenceSet also matches the persisted selection, so evaluation cannot rely only on a caller-supplied ID/reference pair. This establishes historical selection authenticity within the trusted SQLite repository boundary; it is not a cryptographic tamper-proof log and does not protect against direct database-file rewriting.

## Deliberate non-goals

- No Bayesian probability updates or numerical confidence scores.
- No decision-theoretic action selection.
- No autonomous response or execution.
- No persistence of Proposition, HypothesisSpecification, findings, or evaluation records.
- No arbitrary Python evaluator callbacks.
- No claims of actor attribution or authorization from account identity alone.

These remain later layers. M2.4 first makes the evidence-to-proposition and finding-to-diagnosticity path explicit, deterministic, auditable, and testable.
