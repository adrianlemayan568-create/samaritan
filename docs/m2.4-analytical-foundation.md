# M2.4 — Structured propositions and deterministic reasoning

## Scope

M2.4 establishes the analytical contract layer between validated evidence and later probabilistic or decision-oriented reasoning. It does not add analytical database tables or change ingestion, identity, correlation, or persistence schemas. Contracts are immutable and can be validated in memory before persistence is designed.

## Proposition semantics and construction are separate

    EvidenceSet
        -> exact construction definition + exact semantics definition
        -> source resolution
        -> typed role binding
        -> field-level provenance
        -> semantic validation
        -> structured Proposition

A PropositionSemantics definition owns the meaning of a proposition type and version: declared roles, role kinds and types, temporal constraints, temporal scope, and typed parameters. A PropositionConstructionDefinition owns only the finite source bindings used to populate those semantic fields. Construction cannot add or reinterpret fields.

Registries reject duplicate identities. A constructor must request the exact construction ID/version and the exact proposition type/semantics version. There is no fallback to a newer or older semantics version.

## Structured proposition identity

A Proposition contains:
- proposition type and exact semantics version;
- named entity and event role values;
- concrete UTC temporal scope and boundary inclusivity;
- field-level source event, observation, and relationship provenance;
- exact construction ID/version for audit.

The proposition ID is a deterministic UUID5 over semantic identity: proposition type/version, role names and concrete role values, temporal scope, and parameters. Construction history and generation history are deliberately excluded. Therefore the same semantic proposition constructed by different registered construction definitions retains the same proposition identity.

StructuredHypothesis owns a structured Proposition. HypothesisGeneration remains a separate record describing how a candidate was generated; it is not part of proposition identity.

## Initial supported construction

The first registered construction is account_authentication_sequence@1. The finite construction contract also supports registered top-level event-attribute parameters, integer temporal-difference parameters derived from event timestamps, and string parameters sourced from explicit directed relationship records. Relationship retrieval is performed through the repository; each such parameter retains the relationship and observation IDs in its field provenance.

It requires exactly one each of:
- authentication_failure, with participant role target;
- authentication_success, with participant role target;
- host_activity, with participant role subject.

Each participant must resolve to exactly one entity of type user_account, and all three mappings must resolve to the same entity ID. A missing or ambiguous event, missing or ambiguous participant, absent entity, wrong entity type, or inconsistent account identity fails construction.

The failure must strictly precede success, which must strictly precede host activity. Each consecutive interval is at most 300 seconds. The temporal scope runs from failure to host activity, inclusive at both boundaries.

Every proposition role has field-level provenance. The account field retains all three source event IDs and their observation IDs. Event roles retain their own event and observation references.

This construction does not infer a common actor, host ownership, authorization, or malicious intent from shared account identity.

## Findings and evaluation

The new proposition_contracts.py and reasoning_contracts.py modules provide the structured M2.4 path. The earlier evaluation_contracts.py contracts remain intact for compatibility; in particular, CriterionEvaluationResult is not modified. The new path uses its own structured Proposition and StructuredHypothesis contracts.

The new reasoning_contracts.py model is stance-neutral:
- CriterionDefinition describes an independently testable condition, its typed JSON parameters, independence group, and whether its evidence is attacker-influenceable.
- CriterionOutcomeDefinition defines finite outcome codes scoped to a criterion type and vocabulary version.
- CriterionFinding records only a factual matched, not_matched, or insufficient result. An insufficient finding has no outcome code and must identify missing information.
- Findings can be reused. They do not contain proposition-specific stance.

A BearingDefinition maps one criterion outcome to judgments for the focal proposition and one alternative. Judgments are ordinal consistency categories: expected, compatible, unexpected, and incompatible. Each bearing records its rationale, basis, author, review state, and whether the criterion is required or contextual.

The implicit residual alternative uses the reserved ID __residual__. Its judgment is fixed to compatible; it is not an editable declared alternative. Evaluation rules bind to a proposition type and exact semantics version, not to a hypothesis-generation rule. Rule IDs and versions are preserved in an immutable registry.

Production synthesis requires approved evaluation rules and approved bearings. Experimental synthesis may use reviewed definitions. CriterionEvaluatorRegistry binds a criterion type and exact evaluator version to a finite built-in evaluator type and an exact typed parameter interface. CriterionEvaluationEngine dispatches only to the supported built-ins: event attribute equality/presence, event-type counts, participant-role/entity-role matching, and temporal-gap checks. HypothesisEvaluationEngine runs the registered criteria, synthesizes the findings, and returns an immutable HypothesisEvaluationRecord containing the EvidenceSet ID, exact evaluation_rule_id/version, findings, and synthesis. No arbitrary callbacks, free-form expressions, or LLM-generated evaluator bindings are introduced.

## Diagnosticity synthesis

DiagnosticitySynthesizer uses explicit ordinal comparisons, not numerical scores or probabilities.

For each declared alternative, it aggregates findings into:
- favors_focal;
- favors_alternative;
- non_discriminating;
- conflicting.

A complete finding that makes the focal proposition incompatible can produce not_supported only when its criterion is not attacker-influenceable. Missing or insufficient required findings prevent a supported conclusion. Supported requires the focal proposition to be favored over every declared alternative; it does not mean the proposition is proven true.

The residual is always compatible and does not block a supported result. The confidence ceiling remains low unless at least one finding is more expected under the focal proposition than under the residual.

## Deliberate non-goals

- No Bayesian probability updates or numerical confidence scores.
- No decision-theoretic action selection.
- No autonomous response or execution.
- No analytical persistence migrations.
- No arbitrary Python evaluator callbacks.
- No claims of actor attribution or authorization from account identity alone.

These remain later layers. M2.4 first makes the evidence-to-proposition and finding-to-diagnosticity path explicit, deterministic, auditable, and testable.
